# M9 学习笔记：最小前端控制台——同一套页面，既看实时事件，也回放真实事件

> 对应里程碑：M9 · 相关决策：[ADR-0008](../adr/0008-console-sse-replay-design-tokens.md)
> 这一阶段给系统加了脸：一个运维控制台（事件列表、事件详情、批准计划），和 GitHub Pages 上的静态站点（定位、架构图、评测摘要、"回放一次真实事件"）。两者是同一套 React 页面，区别只在数据从哪来：API 加 SSE，或者实验环境导出的一个 JSON 文件。

## 1. 这一阶段做了什么

| 类别 | 内容 |
|---|---|
| 视觉探索 | 用第 18 次实验环境运行的真实数据做了 3 个静态方向（Linear 式克制深色、终端风格、高密度浅色运维面板），选定 A |
| 设计 token | `web/src/styles/tokens.css`：颜色（`light-dark()` 一个变量两套值）、字号、4 px 间距网格、圆角、阴影、动效时长和曲线；Tailwind v4 `@theme` 生成工具类；`tokens.test.ts` 检查 38 对文字色/底色在两套主题下都 ≥ 4.5:1 |
| 后端支持 | `GET /incidents/{id}/agents`（Agent 调用树：每一步的耗时、token、费用、推理，以及这一步调用的工具和产出的证据）；`GET /api/v1/stream`（SSE，按租户推审计行和 Agent 活动，`Last-Event-ID` 续传）；`python -m app.console.export`（一个事件页面读到的所有响应存成一个 JSON） |

| 静态站点 | 落地页（一句话定位、流程、架构图、评测摘要，每个数字链接到出处）；回放：按真实时间戳 1×/10×/30×/60× 加速，可拖动；停在"等待审批"，由访客点批准后继续 |

| CI | `web` job：类型检查、格式、单元测试、构建、首屏 JS 预算；`Pages` workflow 部署 `web/dist` |

## 2. 背景知识

### 2.1 SSE、WebSocket 和轮询

| | SSE | WebSocket | 轮询 |
|---|---|---|---|
| 方向 | 服务器 → 浏览器 | 双向 | 浏览器拉 |
| 协议 | 普通 HTTP 响应，`text/event-stream` | 升级为独立协议 | 普通 HTTP |
| 断线续传 | 标准里就有：`id:` 字段 + 重连时的 `Last-Event-ID` 头 + `retry:` | 自己实现 | 无所谓 |
| 代理和负载均衡 | 友好（要关缓冲：`X-Accel-Buffering: no`） | 需要支持 Upgrade | 友好 |

控制台只需要"服务器告诉我有变化"，SSE 正合适。坑在于浏览器自带的 `EventSource` 不能设置请求头，而 API 只认 `Authorization: Bearer`。把 token 放进 URL 会进访问日志，所以这里用 `fetch` 读响应流，自己按规范解析（空行分隔事件、`data:` 多行拼接、`:` 开头是注释也就是心跳、`id:` 记下来、`retry:` 改重连间隔）。

### 2.2 推"变化"而不是推"状态"

SSE 里每条事件只说"事件 X 有一条新审计行"或者"事件 X 的 investigator.metrics 走了一步"。页面收到后让对应的 TanStack Query 失效，由同一套 GET 接口重新取数据。好处：

- 权限、租户隔离、字段裁剪只在 GET 接口里写一次；
- 页面只重新渲染变化的部分（Agent 走一步，只有调用树和诊断用量刷新）；
- 丢了一条事件也不怕：下一次失效会把最新状态取回来。

一次实测（真实 API、真实 worker、录音回放模型）：调查期间调用树和诊断各请求 8 次，事件、审计、计划各 2 次，没有整页刷新。连续的 Agent 事件用 `cancelRefetch: false`，正在路上的请求不会被下一条事件打断重来。

### 2.3 乐观更新

点"批准"时先改本地缓存（计划显示"已批准 · 发送中"，事件状态变成 EXECUTING），再发请求。成功就让缓存失效、取回服务器的真实状态；失败就把 `onMutate` 时保存的旧值放回去，显示服务器给的原因。审批请求带的是页面上那份计划的哈希，计划在你看的时候被修订过，服务器会拒绝，页面回滚。回放里"拒绝"会被拒（录下来的那次运行是批准的），正好演示回滚。

### 2.4 Core Web Vitals 和"流畅"的量化

- **LCP**（最大内容绘制）：首屏最大元素出现的时间。
- **CLS**（累积布局偏移）：已经在页面上的元素被挤动的程度。新插入的元素不算，被它挤下去的元素算。用户输入后 500 ms 内的偏移不算。
- **INP**（交互到下一次绘制）：一次点击或按键到浏览器画出结果的最长时间，< 200 ms 为好。
- **TBT**：主线程被长任务阻塞的总时间，实验室里用它近似 INP。

动画只改 `transform` 和 `opacity`：这两个属性在合成层上做，不触发布局和重绘，掉帧最少。改 `height`、`top`、`width` 会让每一帧都重新布局。所以展开调查树是"内容淡入并下移 4 px"，不是高度从 0 长到 N；进度条是 `scaleX`，不是改宽度；抽屉是 `translateX`。

`prefers-reduced-motion: reduce` 时，CSS 动画和过渡都缩到 0.01 ms，Motion 的 `MotionConfig reducedMotion="user"` 关掉位移动画。

### 2.5 骨架屏和 CLS

骨架屏要和真实内容一样大，否则数据到了还是会跳。更隐蔽的是"分批到达"：详情页 5 个查询各自返回，各区块一个个冒出来，后面的区块就被一次次往下推。第一次 Lighthouse 测回放页 CLS 是 0.226，罪魁就是 Agent 区块被上面后到的根因区块挤下去。改成"整页一个骨架，所有核心查询都到了再一次性替换"后降到 0。

### 2.6 WCAG 对比度

对比度 = (L1 + 0.05) / (L2 + 0.05)，L 是相对亮度（sRGB 去伽马后按 0.2126 R + 0.7152 G + 0.0722 B 加权）。AA 要求正文 ≥ 4.5:1，大字 ≥ 3:1。深色主题里最容易翻车的是"次要文字"和"按钮悬停色"：这里 `tokens.test.ts` 把每对组合在两套主题下都算一遍，深色主题的强调色悬停态一开始只有 3.95:1，就是测试抓出来的。

### 2.7 代码分割和首屏预算

Vite（Rollup）对每个 `import()` 生成独立 chunk。路由用 React Router 的 `lazy`，所以访问落地页只下载落地页需要的代码。重的依赖放在最晚用到的地方：Recharts（约 93 KB gzip）只在证据抽屉第一次打开时加载；Motion 的动画特性用 `LazyMotion` 异步加载，首屏用轻量的 `m` 组件。预算脚本读 Vite 的 manifest，从入口和路由 chunk 出发把静态依赖闭包里的 JS 全部 gzip 后求和，这才是浏览器首屏真正要下的量。

### 2.8 虚拟列表

一千个事件就是一千个 DOM 节点，滚动和重新渲染都慢。TanStack Virtual 只渲染可见的那几十行，每行用 `translateY` 定位。入场动画要放在内层元素上，因为外层的 `transform` 已经被虚拟列表占用了。

## 3. 踩过的坑，以及设计时预先规避的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| `EventSource` 不能带头 | 拿不到 SSE | `fetch` 流式读，自己解析；单元测试覆盖跨块拆分、多行 data、注释、`\r\n` |
| 导出文件 19 MB | 一次 trace 搜索的原始结果有 3 MB | 原始结果超过 64 KB 不导出，保留摘要、大小和 SHA-256；导出后 336 KB |
| 回放的模型延迟都是 0 | 录音回放不记真实耗时，调用树的"耗时"一列全是 0 | 用实验环境导出的真实案例；视觉探索阶段的模拟数据单独标注 |
| 改了事件时间戳，回放全部 miss | 本地联调时把事件的创建时间改成"现在"，结果提示词里的时间变了，请求哈希对不上录音 | 不改录音里的任何输入；回放只依赖原始数据 |
| 预览服务器 404 | `vite preview` 没带 `VITE_SITE=pages`，base 不是 `/sre-blackboard/` | 预览和构建用同一个环境变量 |
| 在 `QueryClientProvider` 外面用 `useQuery` | 回放页白屏 | 回放案例用普通 `fetch` 加载，`QueryClient` 在拿到案例后才创建 |
| 区块分批出现 | 回放页 CLS 0.226 | 一个整页骨架，核心查询全到后一次替换 |
| 等待审批的提示条 | 横幅插在页面顶部，把整页往下推 | 改成固定定位的浮层，只做 opacity 和 translateY |
| tailwind-merge 不认识自定义字号 | `text-sm text-muted` 被当成冲突，字号被删 | `extendTailwindMerge` 注册自定义字号 |
| 正在看的事件从列表里消失 | 默认"Open"筛选，事件一解决就被筛掉了 | 当前打开的事件始终保留在列表里；回放默认"All" |
| 深色悬停色对比度不够 | 白字在 `#6c77dc` 上只有 3.95:1 | 悬停改为更深的 `#525ec8`；测试防回退 |

## 4. 验收结果

| 指标 | 要求 | 结果 |
|---|---|---|
| 首屏 JS（gzip） | < 200 KB | 落地页 111.3 KB，登录 110.9 KB，控制台事件页 133.0 KB，回放 156.6 KB（`npm run budget`，CI 检查） |
| Lighthouse 性能 | ≥ 90 | 落地页：移动 94、桌面 100；回放：移动 91、桌面 100（gzip 静态服务器，Lighthouse 12.8，默认节流） |
| Lighthouse 无障碍 | — | 四项都是 100 |
| CLS | < 0.05 | 落地页 0；回放：移动 0、桌面 0.028 |
| INP | < 200 ms | CPU 4 倍降速、390 px 宽，展开 Agent、打开证据抽屉（含首次加载 Recharts）、批准等交互最慢 88 ms |
| 375 px | 能看事件详情 | 状态条变两行，审批卡片和根因卡片单列，抽屉占满宽度，列表变成独立页面 |
| 深浅主题 AA | 文字对比度 ≥ 4.5:1 | 38 对组合 × 2 套主题，单元测试通过 |
| 动画 | 只用 transform 和 opacity，尊重 reduced-motion | 进度条 scaleX、抽屉 translateX、入场 opacity + translate；骨架和"实时"圆点只改 opacity |
| 实时更新 | SSE 增量、局部刷新 | 真实 API 联调：事件出现在列表里并滑入；调查期间只有调用树和诊断频繁刷新；从控制台批准后走到 RESOLVED |

端到端联调的做法：一个临时 Postgres，真实的 API、worker 和执行器进程，模型和工具回放第 18 次运行的录音，Kubernetes 和 Prometheus 用测试替身；Playwright 用 approver token 登录控制台，等事件出现、点开、等计划、填评论、批准、等 RESOLVED。

## 5. 面试问答

**Q1：为什么用 SSE 不用 WebSocket？**
只需要服务器到浏览器一个方向；SSE 是普通 HTTP，断线续传（`Last-Event-ID`）是标准自带的，对代理友好。代价是浏览器的 `EventSource` 不能带认证头，所以用 `fetch` 读流、自己解析，一百来行，带单元测试。

**Q2：SSE 断了会不会丢事件？**
不会。每条事件的 id 是一个游标（审计序号.模型调用 id.工具调用 id），每条事件带的是"投递完这条之后从哪里继续"，重连时带上最后一个 id，服务器从那里往后查。即使一个批次中途断开，也不会重复或遗漏审计行。没有 id 的新连接从"现在"开始。服务器每 5 分钟主动断开一次，客户端按 `retry` 重连，避免空闲代理在任意时刻掐断。

**Q3：推送完整状态和推送"变化通知"怎么选？**
推变化。完整状态要在流里重做一遍权限、租户、裁剪；而变化通知只是让前端失效几个查询，数据仍然走已有的 GET 接口。丢一条通知也只是晚一点刷新。代价是多一次请求，对控制台这种量级可以忽略。

**Q4：乐观更新失败了怎么办？审批这种敏感操作适合乐观更新吗？**
`onMutate` 先保存旧缓存再改；失败时恢复，并显示服务器的拒绝原因（计划被修订、过期、别人已经决定、自己不能批自己的计划）。安全性不依赖前端：服务器按计划哈希、角色、发起人检查，执行器执行前还会再查一遍。乐观更新只影响显示，而且"发送中"的状态是明确标出来的。

**Q5：回放页面是怎么做的？为什么不直接录屏？**
导出一个事件页面读到的全部 API 响应，回放时把每个响应裁到回放时钟的"此刻"（之前的审计行、Agent 步骤、计划、审批），并像 SSE 一样发变化事件。页面代码和控制台完全一样。录屏不能交互、不能点开证据、也证明不了页面真的能处理增量更新；而这个回放本身就在测增量更新这条路径。

**Q6：你怎么保证"流畅"？**
有数字：首屏 JS 预算在 CI 里卡住；Lighthouse 性能、CLS 和 INP 在验收时测；动画只碰合成层属性；骨架和真实内容同尺寸，且整页一次替换；长列表虚拟化；重依赖（图表）延迟到第一次用的时候加载。

**Q7：CLS 0.226 是怎么查出来、怎么修的？**
Lighthouse 的 layout-shifts 审计指出被挤动的是 Agent 区块。原因是 5 个查询分别返回，根因区块后到，插在 Agent 区块上面。新插入的元素本身不算偏移，被挤动的才算。改成整页一个骨架，全部到齐后一次替换，旧节点被移除、新节点插入，没有"被挤动"的元素，CLS 变为 0。

**Q8：深浅两套主题怎么维护？**
每个颜色变量用 `light-dark(浅, 深)` 写在一起，`color-scheme` 决定取哪个；用户选择存 localStorage，`index.html` 里一段内联脚本在首帧之前设置 `data-theme`，避免闪烁。组件只用语义名（`text-muted`、`bg-panel`），不知道自己在哪个主题。对比度用单元测试守住。

**Q9：Problem Host 和 Event Host 在界面上怎么体现？**
根因卡片上标"problem host"（原因所在的服务）；如果它也是告警触发的服务，再标"event host"；区块标题旁写明本事件的 event host。两者不同的典型情况是下游故障表现为上游的错误，修复必须指向 problem host，策略引擎的 `problem_host` 检查也是这么判的。

**Q10：前端为什么没有用 Next.js？**
这是一个登录后使用的控制台加一个静态站，不需要 SSR 和 SEO 之外的服务端能力；Pages 只能放静态文件。Vite 构建快、产物纯静态、路由级分割简单。
