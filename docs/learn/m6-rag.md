## 2. 背景知识

### 2.1 BM25、`ts_rank_cd` 和 IDF

BM25 给一个词打分时看三样东西：

- 词频，但会饱和，出现十次不是一次的十倍；
- 文档长度归一化；
- **IDF**：这个词在整个语料里有多稀有。

"payment" 出现在一半的文档里，几乎不提供信息；"9999" 只出现在一篇里，命中就很说明问题。

Postgres 的 `ts_rank`/`ts_rank_cd` 只看词频和词之间的距离（cover density），**没有 IDF**。所以这里的"BM25"只是沿用计划里的名字，实际是一个没有 IDF 的近似。评测把代价量出来了（4.2）：在精确标识符的查询上，它的 hit@1 反而比向量检索低。真 BM25 的升级路径是 ParadeDB 的 `pg_search` 扩展，或者外部的搜索引擎。

另一个细节：`plainto_tsquery` 会把所有词 AND 起来。"checkout errors after a release payment looks idle" 要求一个块里同时出现所有词，几乎一条都匹配不上。所以这里把词 OR 起来，靠排序区分。

### 2.2 稠密向量和交叉编码器

- **双塔（bi-encoder）**：查询和文档各自编码成一个向量，比较余弦距离。文档向量可以提前算好，所以快。但查询和文档在编码时互相看不见，细节对不上，比如分不清"payment 坏了"和"checkout 连不上 payment"。
- **交叉编码器（cross-encoder）**：把（查询, 文档）一起送进模型，每个词都能看到对方，所以准。但每个候选都要跑一次模型，不能提前算。

所以标准做法是两段式：便宜的召回（BM25 + 向量）先取几十个候选，贵的重排只看这几十个。

### 2.3 RRF 为什么能融合不同尺度的分数

`ts_rank_cd` 的分数没有上界，而且随文档长度变化；余弦相似度在 [-1, 1] 之间，而且不同模型的分布完全不同。直接加权求和，就得先把两种分数校准到同一个尺度，而这个校准每换一个模型、每改一次语料都会失效。

RRF（Reciprocal Rank Fusion）**只用名次**：一个块的得分是它在每个列表里 `1/(k + 名次)` 之和。

- 名次和分数的尺度无关，所以不用校准。
- k=60 是原论文的经验值，它让曲线变平。两个列表里都排第 2 的块（1/62 + 1/62 ≈ 0.0323），胜过只在一个列表里排第 1 的块（1/61 ≈ 0.0164）。这正是"两路都认可"的意思。
- 代价是丢掉了分数里的"差距"信息：第 1 名领先很多和只领先一点，RRF 看不出来。所以后面还有重排。

### 2.4 为什么要重排

RRF 只是把两份名单合起来，它不知道哪个块真的回答了问题。交叉编码器逐对读查询和块，能分辨"讲 payment 失败怎么表现"和"只是提到了 payment"。

评测里重排把 hit@1 从 0.722 提到 0.741，hit@5 从 0.926 提到 0.981（4.1）。它还给出一个可以设阈值的分数，让"没有相关内容"成为一个能返回的答案。代价是 CPU 上每次约 0.7 秒。

### 2.5 评测集怎么构建

1. **先写查询，再跑检索**。写好以后不按结果改，否则就是在拿测试集调参。改标注必须有文本上的理由，并写进提交说明。
2. **按小节标注，不按块标注**。块的边界随切块参数变化，小节（`RB-PAYMENT#typical-failures`）不变。一个结果块只要包含任一相关小节就算命中，所以两种切块可以用同一份标注评测。
3. **分类型**：
   - 精确标识符：错误原文、指标名，是 BM25 的主场；
   - 换说法的改写：和答案很少共用词，是向量检索的主场；
   - 调查中会问的问题：混合型；
   - 无答案的负例：用来校准阈值。

   分类型报告，才看得出每一路强在哪里。
4. **dev/test 拆分**：阈值只在 dev（奇数编号）上选，test（偶数编号）只报告。
5. **能复现**：报告只依赖语料、查询、模型和代码。CI 重算它，和提交的版本比较，数字是不是真的由 CI 来保证。

### 2.6 为什么知识库的引用不能单独作为结论

运行手册说的是"这类故障通常怎样"，复盘说的是"上次发生了什么"。它们都不是这一次事件的测量。

M6 的复盘恰好写的是和评测场景同类的历史事件（`PM-2026-10-16-RED-HERRING` 讲的就是"发布是干扰项"）。如果允许只引用知识库，Agent 很容易得出"上次是 payment 开关，所以这次也是"。这和 M7 里被拦下的金丝雀犯的是同一类错：用一条看起来合理的先验代替证据。

所以引用校验规定：fact、inference 和根因候选如果只引用了 `kb_search`，就被退回，仍然不改就丢弃。hypothesis 可以只靠运行手册，因为 hypothesis 本来就不需要证据，它的作用就是"值得去查"。工具返回的摘要里也写明了这一点，提示里也写了"数据和运行手册冲突时，以数据为准"。

## 3. 踩过的坑

### 3.1 原设计的切块参数把每篇文档切成了一块

原设计的参数是 target 450 / min 200 / max 700 / overlap 80，是为几千 token 的长运行手册设计的。这个语料的文档平均约 300 token：

- 每个小节都小于 200，被并进前一块；
- 结果 24 篇文档切出 25 块，"按标题切块"名存实亡；
- 其中 3 块还超过了 bge 的 512 wordpiece 上限，向量路只看到了前半段。

没有直接改参数，而是把参数做成消融的一维：`original` 和 `section`（min 0，每个小节一块）都跑一遍，由数字来选（4.3）。教训是：**切块参数是语料的函数，不是常数**。

### 3.2 重叠把代码块拆坏了

切超长小节时，下一块开头会带上上一块末尾 80 个 token 作为重叠。上一块如果以代码块结尾，带过去的那一行正好是收尾的 ```，下一块就以一个"开启"的代码块开头，后面的文字全被当成代码。

单元测试（`test_a_long_section_is_split_with_overlap_and_code_stays_whole`）检查"每块里 ``` 成对出现"，第一次运行就抓到了。修法是：计算重叠时跳过围栏行。

### 3.3 阈值选错了目标

第一版阈值的选法是区分"首条结果相关"和"其他所有情况"。可回答但首条排错的查询被算进了"不该回答"的一边，结果选出 0.998，清空了 63% 可回答的查询。

这把两个问题混在了一起：

- **排序**：首条对不对，由 hit@1 和 MRR 衡量；
- **拒答**：该不该返回东西，由阈值决定。

一条可回答的查询即使首条排错，也不应该被清空。改成只区分"可回答"和"无答案"以后，阈值变成 0.031。报告里现在也带上了每条查询的最高重排分，阈值合不合理可以直接看出来。

### 3.4 小重排模型不会"拒答"

即使目标对了，MiniLM 交叉编码器的分数也分不开两类查询：

- 8 条无答案查询的最高分是 0.015；
- 但有 4 条可回答的查询得分是 0.000。

后者全是换了说法的查询（"how fast are we eating into the monthly reliability allowance"）。这个模型在 MS MARCO 网页问答上训练，词面重叠少时它不认为相关，即使召回和排序都已经把对的块放在第一位。

在 test 上，0.031 的阈值清空了全部 8 条无答案查询，也清空了 22% 可回答的查询，全是换说法的那一类。精确标识符和调查问题一条都没丢。Agent 多半拿错误原文和具体现象去查，所以接受这个取舍，并记下升级方向：更大的重排模型、更多负例重新校准，或者低分结果标成"弱相关"而不是直接丢掉。

### 3.5 字符串被截到 300 字符

工具层对模型看到的摘要有统一的上限，任何单个字符串都会被截到 300 字符（M3 为日志行设计的）。运行手册的一个小节通常有 400–1000 字符，第一版的 `kb_search` 返回的段落被截得只剩开头。

单元测试发现了这个问题。改成按行返回：每行一项，每段总共最多 900 字符，摘要的总上限照常生效。

### 3.6 开发容器下载不了模型

这个云端开发容器访问不了 HuggingFace，但 GitHub Actions 的 runner 可以。处理方式：

- 本地开发用确定性的 `hash`/`overlap` 替身，整条流水线（入库、四种模式、两种切块、阈值）都能跑通，单元测试也用它们；
- 真模型的数字由 CI 的 `retrieval` 任务产生，通过注解读回来，提交成 `eval/retrieval/report.json`；
- 之后每个 PR，CI 都重算一遍并比较。

替身不懂语义，它们的数字不能拿来评价质量，代码注释和 CLI 帮助里都写明了。

## 4. 结果

### 4.1 四种模式（section 切块，54 条可回答的查询）

| 模式 | hit@1 | hit@3 | hit@5 | MRR | Top-3 token | p50 |
|---|---|---|---|---|---|---|
| BM25（ts_rank_cd） | 0.556 | 0.778 | 0.889 | 0.693 | 301 | 2 ms |
| 向量（bge-small） | 0.648 | 0.833 | 0.870 | 0.760 | 256 | 8 ms |
| 混合（RRF） | 0.722 | 0.907 | 0.926 | 0.815 | 294 | 10 ms |
| 混合 + 重排 | **0.741** | **0.926** | **0.981** | **0.841** | 303 | 667 ms |

test 集上（只报告、不调参）混合加重排的 hit@1 是 0.815，hit@3 是 0.926，MRR 是 0.882。

### 4.2 按查询类型（hit@1 / hit@3）

| 模式 | 精确标识符（20） | 改写（16） | 调查问题（18） |
|---|---|---|---|
| BM25 | 0.65 / 0.90 | 0.38 / 0.50 | 0.61 / 0.89 |
| 向量 | 0.85 / 0.95 | 0.44 / 0.75 | 0.61 / 0.78 |
| 混合 | 0.90 / 1.00 | 0.56 / 0.75 | 0.67 / 0.94 |
| 混合 + 重排 | 0.90 / 1.00 | 0.56 / 0.75 | 0.72 / 1.00 |

- **两路互补**。BM25 在改写上 hit@3 只有一半；向量在调查问题上 hit@3 最低。混合在每一类上都不低于较好的那一路。
- **没有 IDF 的 BM25 输给了向量**，在它本该最强的精确标识符上也是。错误原文里有大量常见词（failed、request、connection），没有 IDF 时它们和"9999"、"ECONNREFUSED"一样重。
- **改写是剩下的难点**。重排后仍有一条（q36，"a toggle someone forgot to switch back after testing"）在前 5 名里找不到答案。

### 4.3 两种切块

| 切块 | 块数 | 混合 + 重排 hit@1 / hit@3 | 每条结果 token | 重排 p50 |
|---|---|---|---|---|
| original（每篇一块） | 25 | 0.870 / 1.000 | ~324 | 1.5 s |
| section（每小节一块） | 108 | 0.741 / 0.926 | ~101 | 0.67 s |

original 的命中率更高，但尺子不一样：整篇块包含所有小节，命中天然更容易。它给 Agent 的上下文是 3.2 倍，重排慢 2.2 倍，有 3 块超过嵌入上限，而且每段 900 字符的工具上限会截掉大半。所以默认用 section，k=3 时约 300 token 就能拿到答案（hit@3 0.926）。

### 4.4 还没有的数字：Agent 用了知识库会不会更准

`rag` 变体的代码、提示和引用规则都已就位，单元测试和回放都通过了。但它在 live 评测上的表现要用真实模型跑，会消耗订阅额度，所以这次没有跑，等单独确认以后再跑。

有一点要提前说明：复盘写的是和评测场景同类的历史事件，所以这个提升回答的是"重复发生的故障"。要回答"没见过的故障"，需要对每个场景去掉它自己的那篇复盘再测（留一法）。

## 5. 面试问答

**Q1：RRF 为什么能融合不同尺度的分数？k 为什么取 60？**
因为它根本不用分数，只用名次：每个列表贡献 `1/(k + 名次)`。`ts_rank_cd` 没有上界、随长度变化，余弦相似度的分布随模型变化，直接加权就得先校准，而校准每换一次模型就失效。k 越大曲线越平，一个列表里的第 1 名越难压过两个列表都靠前的块。60 是原论文在多个数据集上的经验值，我没有调它：调它需要单独的验证集，这个规模下收益不大。代价是丢掉了分数的差距信息，所以后面接重排。

**Q2：已经有混合召回了，为什么还要重排？**
召回的目标是不漏，重排的目标是排准。双塔模型的查询和文档在编码时互相看不见；BM25 只看词面。交叉编码器把两者一起读，能分辨"讲这个问题"和"提到了这个词"。数字上，重排把 hit@5 从 0.926 提到 0.981，调查类问题的 hit@3 从 0.94 提到 1.00。它还提供一个能设阈值的分数，让"没有相关内容"成为合法回答。代价是 CPU 上每次约 0.7 秒，相对 Agent 一步十几秒的模型调用可以接受。重排超时或失败时退回融合顺序，并标记 degraded。

**Q3：评测集是怎么构建的？怎么防止它自证？**
62 条查询分四类：精确标识符、换说法的改写、调查中会问的问题、无答案的负例。在跑任何检索之前写好，之后不按结果改。相关性按小节标注，所以改切块参数不会让标注失效。阈值只在 dev 上选，test 只报告。报告完全由语料、查询、模型和代码决定，CI 用真模型重算并和提交的版本比较，对不上就失败。剩下的偏差我也写明了：语料和查询是同一个人写的，措辞会相近，所以数字可能偏乐观。

**Q4：为什么知识库的引用不能单独作为结论？**
运行手册和复盘说的是"通常怎样"和"上次怎样"，不是这一次的测量。复盘越像这次的故障，越容易被照搬成结论，这和 M7 金丝雀犯的是同一类错。所以引用校验规定：fact、inference、根因候选至少要有一条实时证据，只引用知识库就被退回。hypothesis 可以只靠运行手册，它本来就是"值得去查"的意思。工具摘要和提示里也写明了"数据和运行手册冲突时，以数据为准"。

**Q5：租户隔离是怎么做的？为什么不靠应用层过滤？**
两条检索 SQL 的 WHERE 里都有 `tenant_id = :tenant`（块和文档两张表都过滤），没有不带租户的检索函数，空租户直接报错。工具层面，租户来自工具上下文（事件属于哪个租户），不来自模型的参数，参数 schema 禁止未知字段，模型想填也填不进去。测试覆盖了：在租户 A 里搜租户 B 独有的内容，四种模式都搜不到；不存在的租户返回空。如果在应用层先取再过滤，一个 bug 就会把别的租户的内容送进提示，而提示会被录音、会被持久化。

**Q6：为什么用 pgvector 而不是专门的向量库？**
已经有 Postgres（ADR-0002），镜像里已经带了 pgvector。知识库和业务数据同库：租户过滤、事务（换文档时块的替换是原子的）、备份、迁移都是一套。规模是每租户 108 块，精确扫描几毫秒，连 ANN 索引都不需要。专门的向量库在千万级向量、复杂过滤时才有优势，换来的代价是多一个有状态服务、多一套隔离和备份。我也写了什么时候该重新考虑：十万级块、需要真 BM25 时先试 `pg_search`。

**Q7：HNSW 加租户过滤有什么坑？**
HNSW 是近似搜索，按图游走找 `ef_search` 个候选（默认 40），然后才应用 WHERE。如果目标租户只占 1%，40 个候选里可能一个都不属于它，返回结果不足 k 条甚至为空，而且不报错。解决方法有：pgvector 0.8 的 iterative scan（不够就继续游走）、按租户分区或建部分索引、调大 `ef_search`。这里的规模用精确扫描，没有这个问题，ADR 里写了到什么规模再加索引、加的时候要注意什么。

**Q8：为什么在本地 CPU 上跑模型，不调用嵌入 API？**
这个项目最紧的约束是订阅额度。嵌入 API 意味着每次入库、每次检索、每次 CI 都要花钱，还要管密钥，离线跑不了。bge-small（33M 参数）和 MiniLM 交叉编码器（22M）在 CPU 上嵌入一个查询几毫秒，重排 20 个候选约 0.7 秒，质量在这个语料上够用（hit@5 0.981）。权重在构建镜像时下载，运行时离线。代价是镜像大约 200 MB，以及重排模型的校准不好（3.4）。

**Q9：消融说明了什么？结果里最让你意外的是什么？**
两路召回互补：BM25 在改写上只有 0.50 的 hit@3，向量在调查问题上最弱，混合在每一类上都不低于较好的一路；重排再把 hit@5 推到 0.98。最意外的是没有 IDF 的"BM25"在精确标识符上 hit@1 比向量低 20 个点：错误原文里全是 failed、request 这类常见词。第二个是小重排模型不会拒答，换说法的可回答查询得分和无答案查询一样低。这两点决定了下一步的升级顺序：先换真 BM25，再换更大的重排或重新校准阈值。

**Q10：如果知识库变成一万篇文档，你会改什么？**
- 入库改成增量的后台任务，按文档哈希判断要不要重做（现在已经是幂等的），嵌入批量做；
- 加 HNSW，带 iterative scan，或者按租户分区；
- BM25 换成 `pg_search` 或外部引擎；
- 文档要有 owner、过期时间和版本，过期的运行手册比没有更危险，检索时降权或者在结果里标出来；
- 评测集要扩，并且由不写文档的人来写查询，减少措辞偏差；
- 检索结果进 M8 的指标：命中率的线上代理（Agent 引用了哪些块）、"无相关内容"的比例、重排延迟。
