# 《SRE Blackboard 设计全书》

这本书只讲一个系统：本仓库的 SRE Blackboard。它是一个面向 Kubernetes 微服务的多 Agent 故障诊断与修复系统：告警进来，几个 Agent 并行调查，写出带证据的根因；再提一个修复方案，经过确定性策略和人工审批后，由独立的执行器去改集群，最后用 SLO 确认真的修好了。

[`docs/learn/`](../learn/README.md) 里的学习笔记按里程碑写，记录"当时做了什么、踩了什么坑"。这本书按**系统结构**写，回答的是另一组问题：

- 整个体系由哪些部件组成，每个部件为什么存在；
- 每个部件里的关键设计是怎么考虑的，用了什么技术、什么参数，为什么是这个值；
- 面试官会从哪里往下挖，怎样回答才说明你真的亲手设计过它。

## 怎么读

- **第一次读**：第 1 章 → 第 7、8、9 章（Agent 和安全是这个项目的核心）→ 第 12 章（评测）→ 第 16 章。
- **准备面试**：每章最后的"面试官追问"先遮住答案自己说一遍，再展开对照。答案都折叠在 `▶` 里。
- **查参数**：每章有一张"参数表"，写了默认值、在哪里配置（`app/core/config.py` 的 `SRE_*` 环境变量）和为什么是这个值。

> [!IMPORTANT]
> **关键设计**：这一处决定了系统的正确性或安全性。换一种做法，系统就会在某种情况下出错。

> [!WARNING]
> **关键问题**：面试官最可能深挖的地方，或者设计上真实存在的局限。答不上来，说明没有真正想过这件事。

> [!NOTE]
> **实测**：来自实验环境或 CI 的真实数字，出处在 [`docs/results.md`](../results.md)。

面试题按难度分三级：

- 🟢 **基础**：做过这个项目的人都应该能答；
- 🟡 **深挖**：要求说清"为什么不用另一种做法"，以及代价；
- 🔴 **压力**：面试官故意找你设计的漏洞，或者把规模放大 100 倍。

## 数字从哪里来

书里的每个数字都来自真实运行或 CI，出处汇总在 [`docs/results.md`](../results.md)。样本小的地方会直说：比如准确率是每个变体在 6 个场景上各跑 1 次得到的。面试时主动说清楚这些边界，比把数字说大更有说服力。
