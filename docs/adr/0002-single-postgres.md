# ADR-0002：用一个 Postgres 承担状态、队列和检索

- 状态：已接受
- 日期：2026-10-12
- 相关里程碑：M1（队列和状态）、M6（检索）

## 背景

原型的设计文档里有 MySQL（业务数据）、Redis（队列、去重、租约）、Elasticsearch（日志和知识库检索）三套存储，但代码里一个都没用上：状态在进程内存和内存版 sqlite 里，去重表是一个模块级 `dict`，审批单是一个进程内单例。结果是：

- API 只能跑一个进程，多开一个就会重复建事件（B3）；
- 进程一重启，事件、任务、审批全部丢失；
- "建事件"和"派任务"不在同一个事务里，中间崩溃就会出现有事件、没任务的情况。

约束：单人维护；本地机器 16 GB 内存，还要跑 kind 集群和 OTel Demo；目标规模是每天几百到几千条告警。

## 决定

1. **只用一个 Postgres 16**（镜像 `pgvector/pgvector:pg16`，为 M6 的向量检索预留）。事件、告警、任务队列、审计日志都在里面；M6 的知识库检索也用它的 `tsvector` 和 `pgvector`。
2. **API 和 worker 进程不持有任何状态。** 去重、任务分派、状态推进全部依赖数据库的约束和事务，所以任意数量的进程可以并行运行。
3. **一次告警接入只用一个事务**：写告警、建或合并事件、建 triage 任务、写审计，要么全部成功，要么全部回滚。因为任务队列就在同一个库里，所以不需要 outbox 模式。
4. **去重靠部分唯一索引，而不是时间窗口。**
   - 索引是 `UNIQUE (tenant_id, fingerprint) WHERE closed_at IS NULL`：同一租户、同一指纹，同时最多只有一个未关闭的事件。
   - 写入时用 `INSERT … ON CONFLICT DO NOTHING`；冲突了就 `UPDATE` 已有事件的 `alert_count`。
   - 计划初稿写的是 `UNIQUE(tenant_id, fingerprint, dedup_window)`，按 10 分钟分桶。它有边界问题：相隔 1 秒、但正好跨过桶边界的两条告警，会建出两个事件。改成"一个指纹同时只能有一个未关闭事件"之后，语义变成"事件关闭前，同类告警都合并进来"，和 PagerDuty 的 `dedup_key` 一致。
5. **表结构用 SQLAlchemy Core 定义，用 Alembic 管理迁移。**
   - 测试会把迁移降到底再升到顶。
   - 另有一个测试检查迁移结果和代码里的表定义完全一致。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| MySQL + Redis + Elasticsearch（原设计） | 每个组件都是各自领域的主流选择 | 三套运维；建事件和派任务跨两个系统，需要 outbox 或分布式事务；本地内存放不下；这个规模用不上它们的性能 | 不采用 |
| Postgres + Redis（队列放 Redis） | Redis 队列延迟更低 | 入队和业务写入不在一个事务里，仍然需要 outbox；Redis 的持久化和租约要自己处理 | 不采用 |
| 只用 Postgres | 一个事务覆盖所有写入；约束由数据库保证；一套备份和监控 | 队列吞吐有上限（见 ADR-0003）；检索能力不如专用搜索引擎 | **采用** |

## 后果

- 正面：
  - 幂等和"不重复领取"由数据库约束保证，不靠应用代码里的判断，压测可以直接验证；
  - 本地只多一个容器，压测后的空闲内存占用约 40 MB；
  - 备份和恢复只涉及一个系统。
- 代价：
  - Postgres 成了单点。生产环境需要主从复制和自动切换，不在本项目范围内，但在面试中要能讲清楚；
  - 合并告警时会更新事件行。同一事件的告警洪峰会在这一行上排队，压测中 50 个并发请求打同一指纹没有问题；
  - 审计日志的追加用一把全局 advisory lock 串行化，写审计的事务吞吐受限。目前只有建事件和状态变化才写审计，告警合并不写。
- 什么情况下应该重新考虑：
  - 单库写入成为瓶颈，比如每秒上千个新事件；
  - 知识库检索的质量或规模超出了 `tsvector` + `pgvector` 的能力；
  - 需要跨地域多活。
