# ADR-0008：控制台用一套页面、两种数据源；SSE 只通知"什么变了"；设计 token 和性能预算写进 CI

- 状态：已接受
- 日期：2026-10-27
- 相关里程碑：M9

## 背景

M9 要两样东西：一个运维用的控制台（看事件、看 Agent 怎么查的、批准计划），和 GitHub Pages 上一个"回放一次真实事件"的静态页面。约束：

- 页面要好看、流畅，并且有量化验收：动画只用 transform 和 opacity，CLS < 0.05，Lighthouse ≥ 90，INP < 200 ms，首屏 JS gzip 后 < 200 KB，375 px 宽能用，深浅两套主题都过 WCAG AA。
- Pages 是纯静态的，没有服务器，也不能放 token。
- API 已经是无状态的多进程（M1），事件的每一步都写在 `audit_log`、`llm_calls`、`tool_calls` 里（M4、M5）。
- 浏览器的 `EventSource` 不能带 `Authorization` 头，而 API 只认 bearer token。

## 决定

1. **一套页面，两种数据源。** 页面只依赖一个 `Source` 接口：`get(path)`、`subscribe(onChange)`、`decide(...)`。控制台用 `LiveSource`（真实 API 加 SSE）；Pages 用 `Replay`：读 `python -m app.console.export` 导出的 JSON（按 API 路径存的响应），把每个响应裁到回放时钟的"此刻"（这之前的审计行、Agent 步骤、工具调用、计划、审批），并且像 SSE 一样报告变化。事件详情页不知道自己在回放。
2. **SSE 只说"什么变了"，页面自己去取。** `GET /api/v1/stream` 推两种事件：一条审计行（状态转换、计划、审批、执行、验证），或者"这个事件的这些 Agent 走了一步"。前端按事件类型失效对应的 TanStack Query key（`staleFor`），只有那几个查询重新请求。游标是 `审计序号.模型调用 id.工具调用 id`，断线后用 `Last-Event-ID` 续上，不丢不重。SSE 用 `fetch` 加流式解析实现，这样能带 bearer token。
3. **审批是乐观更新。** 点"批准"后页面立刻显示已批准、状态变成 EXECUTING；API 拒绝（计划被修订、过期、别人先决定了、自己不能批自己的计划）就回滚并显示原因。审批请求带着页面上看到的计划哈希。
4. **设计 token 是唯一的取值来源。** 颜色、字号、间距、圆角、阴影、动效时长和曲线都在 `web/src/styles/tokens.css`，每个颜色用 `light-dark()` 同时写深浅两个值，通过 Tailwind v4 的 `@theme` 生成工具类。组件里没有裸色值。`tokens.test.ts` 重算每一对文字色和底色的对比度，低于 4.5:1 测试就失败。状态和严重度只有一套语义色（accent、success、warning、danger、critical）。
5. **性能预算进 CI。** 路由级代码分割（落地页、登录、控制台、回放、事件详情各自一个 chunk；Recharts 只在证据抽屉第一次打开时加载；Motion 的动画特性在首屏之后加载）。`npm run budget` 读 Vite 的 manifest，算每个入口路由首屏要下载的 JS（入口加路由 chunk 加它们的静态依赖）gzip 后的大小，超过 200 KB 就失败。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Pages 上单独做一个回放动画页 | 简单 | 和真实控制台是两套东西，又会变成"脚本化演示"（原型的问题） | 不采用 |
| 回放时把整个状态预先算成帧，按帧播放 | 播放逻辑简单 | 页面得为回放写一套渲染；改一处要改两处 | 不采用：用"裁到此刻"的 `Source` |
| SSE 推完整的新状态 | 前端不用再请求 | 每个事件要拼一份完整响应，权限和裁剪逻辑要在流里重写一遍 | 不采用：推变化，前端走同一套 GET |
| WebSocket | 双向 | 这里只需要服务器到浏览器；要自己做重连和续传；对代理不如 SSE 友好 | 不采用 |
| `EventSource` 加 token 放在 URL 查询参数里 | 浏览器原生重连 | token 会进访问日志和浏览器历史 | 不采用：`fetch` 流式读，自己解析 |
| 前端轮询 | 最简单 | 延迟和请求量不可兼得；"局部刷新"做不到精确 | 不采用 |
| CSS-in-JS 或组件库自带主题 | 现成 | 运行时开销；token 分散 | 不采用：CSS 变量加 Tailwind |
| shadcn/ui 整套生成 | 组件多 | 大部分用不上 | 只按 shadcn 的写法放了 Button、Badge、Skeleton、Sheet（基于 Radix Dialog） |

## 后果

- 正面：Pages 的回放走的是控制台的同一份代码和同一条更新路径，回放能用就说明增量更新能用；数据来自实验环境的真实导出，不是手写的。CI 能挡住对比度和首屏体积的回退。
- 负面或代价：回放只能展示导出时已有的数据，超过 64 KB 的原始工具结果不进导出（摘要、大小和哈希还在）。SSE 的服务端是每个连接轮询数据库（默认 1 秒），连接数多了要换成 `LISTEN/NOTIFY`。`light-dark()` 需要 2024 年以后的浏览器。
- 什么情况下应该重新考虑：同时在线的控制台超过几十个（换 `LISTEN/NOTIFY` 或一个推送进程）；需要从控制台发起更多写操作（再评估乐观更新的回滚体验）；Pages 要回放多个事件并互相对比（导出格式加版本迁移）。
