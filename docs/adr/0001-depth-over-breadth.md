# ADR-0001：深度优先，只做一条真实闭环

- 状态：已接受
- 日期：2026-10-10
- 相关里程碑：M0（影响全部里程碑）

## 背景

第一版原型约 2000 行 Python，覆盖了 30 多个概念：双模型网关、10 阶段流水线、13 个 Agent 角色、R0–R4 风险分级、经验记忆、技能自演化、在线指标、代码分析、混合检索、100 样本评测等。但每个概念只有 15–150 行，而且：

- 没有任何真实的模型调用（`StubModel` 永远返回 `finish`）；
- 工具返回伪造的证据 ID，Agent 产出写死的结论；
- 评测的期望值由被测函数自己生成，指标必然是 100%；
- 模型名和价格是虚构的；
- README 描述的能力远多于代码实际做到的。

这是一个简历项目，面试官会挑一个点往深里问。广度大、深度浅的代码，经不起五分钟的代码审阅。

## 决定

1. **先做一条真实闭环，做扎实，再横向扩展。** 这条闭环是：注入故障 → SLO 告警 → 真实 LLM Agent 用真实工具取证 → 带证据链的根因 → 策略检查 → 人工审批 → 回滚 → 验证 SLO 恢复。
2. **任何时刻，README 只描述 `main` 上已经实现的内容。** 计划中的内容放在路线图和 `docs/plan/` 里，明确标注为"计划"。
3. **M0 直接删除没有真实行为、也没有接入任何流程的模块**，不保留"以后再说"的空壳：
   - `evolution.py`、`online.py`、`code_analysis.py`、`limits.py`：只有常量和几行规则，没有被任何流程使用；
   - `status.py`：按墙钟时间推进的假看板；
   - `e2e.py`：写死的端到端脚本；
   - `ext.py`：能连接 MySQL/Redis/ES，但没有任何业务代码使用这些连接；
   - `observe.py`、`store.py`：只有常量定义；
   - `skills/*/scripts`：每个 5 行的占位脚本。

   这些代码保留在 git 历史中；其中有价值的设计想法记录在下面的"未来工作"一节。
4. **仍然参与流程的原型模块暂时保留**（harness、agents、queue、persistence、safety、rag 等），但删除夸大的注释，并在 README 中如实标注状态。它们会在 M1–M6 中按计划被替换。
5. **删除对不公开规格文档的引用**（代码里的 `Sec.x.y` 注释）。仍然有效的规格内容转写成公开的 ADR。
6. **删除或下线没有鉴权、行为是伪造的 HTTP 接口**（审批、事件详情、报告、状态、指标）。在正确实现之前，宁可不提供，也不提供一个不安全或者是假的版本（fail-closed）。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 保留全部模块，逐个补实现 | 看起来功能多 | 战线太长，每个都做不深；空壳期间 README 依然不诚实 | 不采用 |
| 新开仓库从零开始 | 没有历史包袱 | 丢失演进历史，而"如何把原型改造成生产系统"本身就是好的面试素材 | 不采用 |
| 在原仓库按里程碑重构，先删空壳 | 历史可追溯；每个里程碑都可以独立演示 | 中途有一段时间功能看起来比原来少 | **采用** |

## 后果

- 正面：仓库在任何时刻都经得起审阅；面试时可以讲清楚每一行代码；git 历史展示了从原型到生产的演进过程。
- 代价：M0 之后，仓库能"展示"的功能比原型少，要到 M4/M5 之后才能演示完整的闭环。
- 什么情况下应该重新考虑：如果核心闭环（M0–M5）已经稳定，并且评测数据证明它有效，再考虑恢复经验记忆、技能演化这类扩展能力。

| 经验记忆 | `memory.py` | 复盘文档写入知识库，由 RAG 检索 |
