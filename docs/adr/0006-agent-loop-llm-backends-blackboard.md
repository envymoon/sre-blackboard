# ADR-0006：手写 Agent 循环、可插拔 LLM 后端、黑板检查点与引用校验

- 状态：已接受
- 日期：2026-10-15
- 相关里程碑：M4（覆盖初稿的 ADR-0004、0005、0006、0012、0013）

## 背景

M3 之后，Agent 已经能查到真实数据。M4 要让真实的 LLM 用这些数据做诊断：告警进来，产出一份带证据链的根因报告。同时有几条约束：

- **额度**：默认用 Claude 订阅额度（`claude -p`，Haiku），不是按量计费的 API。订阅有用量窗口，并发要低。
- **可测试**：LLM 不确定，CI 和云端开发容器里也没有模型和集群。没有确定性的回放，Agent 就没法做回归测试。
- **防幻觉**：原型里结论引用的是伪造的 `EV-xxxxx`。现在每个结论都必须指向一行真实存在的证据。
- **会崩溃**：worker 会被杀、租约会丢（M1）。一次调查要调用模型二十次左右，重来一遍既费额度，也会得到不同的结论。

## 决定

**一、后端只回答"下一步是什么"**

1. 后端接口只有一个方法：给定渲染好的 transcript，返回下一步。下一步要么是至多 3 个工具调用，要么是最终答案。循环、工具执行、校验都在我们自己的代码里（`app/agents/loop.py`）。
2. 三种后端实现同一个接口：
   - `ClaudeCLIBackend`：每步启动一个 `claude -p`。用我们的系统提示替换 Claude Code 自带的；关掉全部内置工具、MCP 和本机设置；用 `--json-schema` 约束输出。模型什么也执行不了，只能提议。
   - `AnthropicAPIBackend`：原生 `tool_use` / `tool_result`。最终答案也是一个工具（`submit_final`），`tool_choice: any` 保证每步不是调用就是答案。工具定义、系统提示、已有 transcript 三处设缓存断点。
   - `ReplayBackend`：按 `(agent, prompt 版本, 请求哈希)` 从录音里取答案。请求哈希覆盖模型看到的全部内容。
3. CLI 后端的数据源只写在输出 schema 里（`actions` 的每个分支带描述和参数 schema），不写进系统提示。探针发现：写进系统提示时，Haiku 会先把它们当成原生工具去调，失败后才改用 `actions`，每步白白多一轮。改了以后，提示 token 减半，延迟从 4.7 秒降到 3.2 秒。
4. 错误分类：限流、过载、超时、进程崩溃会重试（指数退避加抖动）；认证失败、请求错误、回放未命中不会重试。限流给出的等待时间超过 2 分钟时直接放弃。订阅窗口可能要几小时才恢复，在 job 里干等会一直占着租约；放弃后由队列稍后重试整个 job。
5. 每个进程同时最多 2 个 `claude -p`（每个约 250 MB）。每个角色的模型可以单独配置，默认全部 `claude-haiku-5-5`。

**二、一次调查的流程**

6. Coordinator（无工具，一步）写计划：已知情况、假设、给每个 Investigator 的任务。
7. 3 个 Investigator 并行：`metrics`（Prometheus）、`logs_traces`（Loki + Jaeger）、`changes`（发布历史、配置差异、事件、feature flag）。每个最多 8 步，最后一步只能给答案。并发用 `TaskGroup`：一个碰到预算或限流，其他的会被取消，而不是继续跑没人收的结果。
8. Synthesizer（无工具，一步）读全部 Finding，写结构化的 `Diagnosis`：排好序的根因候选、事实、高置信推断、待验证假设。Markdown 报告只是它上面的模板。

**三、引用校验（确定性，不用模型）**

9. 每个被引用的证据 ID 必须：(1) 存在且属于本事件；(2) 出现在引用者看到过的结果里（Investigator 只能引用自己查到的，Synthesizer 只能引用被接受的 Finding 引用过的）；(3) 类型匹配，比如"日志"类结论至少引用一条日志查询。事实和推断至少要有一个引用，假设可以没有。
10. 不合格时，把问题清单退回给模型一次；第二次还不合格的条目丢弃，丢弃数记在运行记录里。没有一个根因候选站得住时，事件转 ESCALATED，不硬猜。

**四、黑板与检查点**

11. `agent_runs` 每个事件每个 Agent 一行（唯一约束），这就是检查点。`blackboard` 只追加：计划、Finding、诊断，每行属于写它的 Agent。一个 Agent 的输出和"它完成了"写在同一个事务里，要么都在，要么都不在。
12. 检查点的写入走 job 的 fence（M1）：丢了租约的 worker 还能把模型调用跑完，但什么也记不成"完成"。模型调用的账单（`llm_calls`）不受 fence 限制，因为 token 确实花掉了。
13. job 重跑时，已完成的 Agent 直接从黑板读结果，不再问模型；被打断的 Agent 从头再来，它的工具调用会复用已有的证据行（证据 ID 由内容派生，ADR-0005）。INVESTIGATING 是恢复点。

**五、预算与用量**

14. 每一步之前检查事件已用的 token（提示 + 输出，缓存的也算），超过上限就转 ESCALATED。用量和"等价 API 成本"取自后端返回的 `usage` 和 `total_cost_usd`，不维护价格表。

**六、录制与回放**

15. 不额外写录音文件：数据库本身就是录音。`llm_calls` 存了每一步的请求哈希和模型的回答，`tool_calls` 加 `evidence` 存了每次工具调用的原始结果。`app/agents/recording.py` 把一次调查导出成录音；回放时把事件行装进空数据库，用同一份代码再跑一遍。
16. 为了让回放可重复，渲染给模型的内容只来自已存储的行，不读时钟。所以描述里不写不断增长的告警计数，标注取第一条通知的，"相关事件"按创建时间和关闭时间计算，并且只算本事件打开时已经打开的（同一波告警分属不同 webhook，相差几毫秒提交，往后看就取决于时机）。并行的 Investigator 可能几秒内发出同一个查询，同一故障的几个事件也会问同样的问题，所以工具录音按事件、再按提问的 Agent 分别回放。

## 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| Agent 循环 | LangGraph / 其他框架 | 不采用：要的只是"渲染 → 一步 → 校验 → 执行"，几十行代码；框架会把状态藏起来，检查点、fence、回放都要绕着它做 |
| | 让 Claude Code 自己跑循环（把工具做成 MCP server） | 暂不采用：循环不在我们手里，就做不了逐步预算、引用校验、按步回放；留作对照实验 |
| | **手写循环，后端只答一步** | **采用** |
| 默认后端 | Anthropic API | 有 key 时可用，同一个接口；默认不用，因为额度来自订阅 |
| | **`claude -p` 单步** | **采用**：代价是每步要起一个进程（约 1 秒），而且 transcript 是一整块文本，前缀缓存用不上（第 3 条之外的已知成本，见学习笔记） |
| 结构化输出 | 让模型输出文本再解析 | 不采用：CLI 的 `--json-schema` 和 API 的工具输入都能直接约束形状 |
| Agent 之间的协作 | Agent 互相对话 | 不采用：对话难以检查点、难以回放、容易互相带偏；黑板上每个 Agent 只写自己的行 |
| 检查点粒度 | 每一步 | 不采用：要存完整 transcript，恢复逻辑复杂；一个 Investigator 重跑的代价只有几步 |
| | **每个 Agent** | **采用**：满足"已完成的 Investigator 不重复调用" |
| 防幻觉 | 让另一个模型审核 | 不采用：审核本身也会出错，也不可测；ID 是否存在、是否看过、类型是否匹配都能确定性检查 |

## 后果

- 正面：
  - 同一套代码面对不同故障给出不同的根因，每个结论都能点开看到原始数据和哈希。
  - 整个调查可以在 CI 里逐字节回放：不用模型，不用集群，不花额度。
  - worker 中途被杀，接手的 worker 只补做没完成的部分。有一个测试就是真的 SIGKILL 一个进程来验证的。
- 代价：
  - 用 CLI 时每步都要重发整个 transcript，而且都按"写缓存"计费。一次调查约 20 步、15 万 token（Haiku 约 0.03 美元等价成本）。API 后端有增量缓存，便宜得多。
  - 每个 Agent 粒度的检查点意味着被打断的 Investigator 要重问一遍模型，这次答案可能和上次不同。
  - 回放对任何改动都敏感：改一个字的 prompt，旧录音就失效。这是有意的，但也意味着录音要随 prompt 一起更新。
- 什么情况下应该重新考虑：
  - 有了 API key 且调用量大：默认后端换成 API。
  - 单个 Agent 步数变多（几十步）：改成按步检查点。
  - 要和其他客户端共用工具：把工具包装成 MCP server，循环仍留在这里。
