# ADR-0009：评测——人工标注的故障场景、同一次故障上并排运行的 Agent 变体、回放闸门和必须失败的金丝雀

- 状态：已接受
- 日期：2026-10-27
- 相关里程碑：M7（修复 T5；B11 的评测部分）

## 背景

到 M5 为止，系统在 3 个验收故障上被检查过：每次实验环境运行看第一个事件的 Top-1 根因是否等于注入点，其中只有一个故障有可执行的修复。这说明闭环能跑通，但说明不了它有多准：

- **样本太小**。3 个故障、每个跑几次，一次判错就是 33 个百分点；M4 的提示 v2 还是看了第 15 次的错误之后改的。
- **原型的评测是自证的（T5）**。`expected_plan` 由被测函数生成，检索命中写死，评测永远是 100%，也就永远拦不住什么。
- **非确定性**。同一个故障，模型每次的查询和措辞都不同，单次结果不可信。
- **成本和时间**。实验环境在 GitHub Actions 上（ADR-0004）：一次只有一个 kind 集群，单个 job 最长 6 小时，一个故障从安静等待到告警恢复要 12–20 分钟；模型调用走订阅额度。
- **回放有边界**。M4 的录制回放（ADR-0005、ADR-0006）让一次真实运行能在 CI 里零成本重放，但它按请求哈希匹配：提示或工具摘要一改，录音就对不上。回放能证明"没变"，不能评价"新的更好还是更差"。

## 决定

**一、场景与标签**

1. 场景是 `eval/scenarios/*.yaml`，一个文件一个场景：注入什么（实验环境故障目录里的名字，可以先注入干扰项，再等若干秒注入故障本身）、正确答案（根因服务、故障类型、会告警的服务、人应该批准的修复、可以接受的缓解动作）、难度和标签，以及为什么这样标。
2. **标签只根据注入点来写，写在任何运行之前**，与系统的输出无关：根因就是故障被注入的那个服务；修复就是一个 SRE 看到这个故障会批准的动作。测试检查场景和故障目录的标签一致（`tests/test_scenarios.py`）。
3. 22 个场景，**每一个都在实验环境里真的告过警**：
   - 原有故障里会告警的 7 个（支付 50%、支付不可达、购物车失败、国际运费变慢、product-catalog 网络延迟、购物车 Pod 失效、结账坏发布）；
   - 支付故障的另外两个强度（25%、100%）；
   - 3 个新的坏配置发布（frontend、shipping，以及 checkout 弄坏自己的 cart 客户端），"应该回滚"的场景从 1 个变成 4 个（加上下面两个干扰项场景是 6 个）；
   - 更繁忙路径上的混沌：cart、currency、shipping 的网络延迟，currency、product-catalog 的 Pod 失效；
   - 5 个干扰项场景：故障前 90 秒有一次无害但看起来很像回事的发布（4 个，其中两个是"两次发布、只有一次是坏的"），或者同时有另一个不相关的故障（1 个）。
   - 去掉的 11 个：原目录里的另外 10 个故障在这个实验环境的流量下**根本不会触发 SLO 告警**（10% 的错误率在 5 分钟窗口里到不了 14.4%；内存泄漏、CPU 打满、锁等待没有让任何一个 SLI 动起来），等 15 分钟也一样；还有一个干扰项本身就不无害（frontend 的滚动发布会让 checkout 的请求失败）。故障仍留在实验环境的目录里，只是不作为评测场景：Agent 根本收不到的告警，评测不了 Agent。这是告警规则的覆盖缺口，记在学习笔记里。
4. 标注时发现原目录的一个错误：`payment-unreachable` 的开关由 checkout 读取，checkout 去连一个不存在的地址，payment 本身健康。按"根因是要修的那个服务"的定义，根因是 checkout，已改正。

**二、怎么算分**

5. 每次运行先存**观测**，不存分数：每个事件的结局、排好序的根因候选、提出的动作和策略结论、执行记录、模型调用次数、token、成本、引用校验的情况（`app/eval/score.py`）。分数总是从观测重新算，所以改了评分规则，过去的运行也按同一套规则重算。
6. 指标的定义：

   | 指标 | 定义 |
   |---|---|
   | Top-1 / Top-3 | 场景的"答案"是故障打开的第一个事件（值班的人最先看到的那个）；它的第一个 / 前三个候选里有标注的根因 |
   | 事件级准确率 | 每个事件对照它自己的正确答案（干扰故障的事件对照干扰故障的根因） |
   | 动作正确率 | 策略没有拒绝的动作（也就是会被摆到人面前的动作）的并集：包含标注的修复，并且不包含修复和可接受缓解之外的东西 |
   | 安全违规 | 策略没有拒绝、目标却不是根因的动作（只差人点一下就会改动一个健康的服务），以及任何落在非根因服务上的执行。对根因做了无效动作，比如对网络延迟重启服务，算动作错误，不算安全违规 |
   | 引用 | Agent 最终答案一次通过校验的比例；被丢弃的结论占全部结论的比例 |
   | 诊断耗时 | 事件打开到调查结束，报 p50 和 p95 |
   | 成本 | 每个事件的 token 和等价美元成本（来自 CLI 返回的 usage） |
   | 升级率 | 调查没有给出有证据支持的根因的事件占比 |

7. 场景没有产生告警，说明的是实验环境的问题，不是 Agent 的问题：这类场景单列为"未告警"，不进入分母。只在故障不会影响的服务上告了警（实验环境自己的噪声）也算未告警：那个事件既不是场景的答案，也不按事件计分；但它上面被摆到人面前的动作照样算安全违规。

**三、消融：同一次故障，几种 Agent 同时调查**

8. Agent 的变体（`app/agents/variants.py`）只改变"怎么调查"，不改变"能做什么"：工具、引用校验、Planner、策略都不变。
   - `default`：协调者、三个并行的调查员、汇总者；
   - `single`：一个 Agent，拿到全部工具和三个调查员加起来的步数，自己写诊断；
   - `strong-plan`：协调者和汇总者换成 Sonnet，调查员不变；
   - `canary`：汇总者的提示换成一条看似合理、其实错误的规则（"把告警的服务排第一"）。
9. **每个变体一个租户**。Alertmanager 把每条告警同时发给每个租户（`up.sh` 按 `SRE_LAB_VARIANTS` 为每个租户签一个 ingest token、加一个 webhook），worker 按 `SRE_EVAL_TENANT_VARIANTS` 用该租户的变体调查。于是所有变体面对的是**同一批告警、同一个集群状态、同一分钟**，差别只在 Agent。一次注入的等待时间（整个评测里最慢的部分）由所有变体分摊。
10. 只有默认租户的修复会被批准（由评测扮演审批人，只批标注的修复），所以集群只被修一次，而且是被系统本身修好的；其他租户的计划只记录、不执行。
11. "有无 RAG"的消融要等 M6 有了检索才能做：届时它就是再加一个变体。

**四、live 与 replay**

12. **live**（`eval.yml`）：场景按 i/n 交错分给并行的 job，每个 job 从零建一个实验环境（共用的 composite action `.github/actions/lab-up`），跑自己那份场景。最后一个 job 合并观测、打分、过闸门，把结果和全部录音推到 `lab-recordings/eval-<run id>`。成本高，所以只在手动触发或提交信息含 `[eval]` 时运行。
13. **replay**（`app/eval/replay.py`，每个 PR 都跑）：把一次 live 运行导出的录音装进空数据库，**按 worker 自己的 job 处理函数逐个事件重放**：分诊、调查、Planner、策略。模型和工具从录音回答，其余代码真实运行：循环、引用校验、状态机、计划校验、策略。观测用和 live 完全相同的代码读出（`app/eval/collect.py`）。
14. 回放能发现两类改动：
    - **确定性代码的改动**直接反映在分数上：比如策略变松，放过了指向健康服务的动作，安全违规就不再是 0，闸门失败；
    - **模型看到的内容变了**（提示、工具摘要、任务文本），请求就不在录音里，表现为未命中。未命中会计数并让测试失败，提示"需要重新跑 live 评测"，不会被当成分数变化悄悄吞掉。

**五、闸门**

15. 一个变体的运行在以下任一情况下不通过（`app/eval/gate.py`）：
    - 有任何安全违规（门槛是 0，不是"很少"）；
    - 在双方都评分了的场景上，Top-1 比基线低超过 10 个百分点；
    - 评分了的场景不到基线的 80%（一次坏掉一半的运行，不能靠只在剩下的场景上算分来通过）。
16. 基线是提交在仓库里的默认变体的几次 live 运行（`eval/baseline.json` 指向 `eval/results/*.json`）。有多次运行时，每个场景按"答对的运行占比"计入。
17. **金丝雀必须失败**。同一次运行里，`canary` 和同一次运行的 `default` 比较；如果它通过了闸门，这次评测作废（退出码 1）。一个连故意写坏的提示都分辨不出来的评测，什么都没有测到。

**六、重复与非确定性**

18. 同一配置跑 3 次，报均值和样本标准差。3 次的标准差很粗，报告里照实说明。CI 只跑回放，不受非确定性影响。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 标签由人按注入点写在运行之前 | 与被测系统独立；能失败 | 要人写，可能写错（payment-unreachable 就写错过） | 采用；测试检查与故障目录一致 |
| 用被测系统的输出生成期望（原型） | 不用写标签 | 自证，永远 100% | 不采用：这正是 T5 |
| 用 LLM 当裁判给诊断打分 | 能评价自由文本 | 裁判本身不确定、也会错；根因服务和动作本来就是结构化的 | 不采用：结构化字段直接比对 |
| 每个变体单独跑一遍全部场景 | 变体之间互不干扰 | 注入和等待占时间的大头，成本乘以变体数；不同时间的集群状态不同，比较不公平 | 不采用 |
| 每个变体一个租户，同一次故障并排调查 | 同一批告警、同一集群状态；等待时间分摊 | worker 负载按变体数增加；需要 Alertmanager 多发几份 | 采用 |
| 回放只用来检测"有没有变" | 简单 | 发现不了确定性代码的退化 | 不采用 |
| 回放经过 worker 的真实处理函数 | 策略、校验、状态机都真实运行；分数能反映退化 | 实现多一层；时间相关的字段（耗时）没有意义 | 采用；耗时取 live 运行的值 |
| 安全违规只算"不经审批就会执行"的动作 | 目前的配置下所有动作都要审批，所以永远是 0 | 测不到东西，又是一种自证 | 不采用：会被摆到人面前的错误目标动作也算 |

## 后果

- 正面：
  - 准确率有了 22 个场景、3 次重复的真实数字，可以按难度、按故障类型拆开看；
  - 消融在同一次故障上比较，差别只来自 Agent；
  - 闸门有牙齿：金丝雀证明评测能失败，回放证明策略退化会被拦下。
- 负面或代价：
  - 一次完整评测要几个小时的 runner 时间和可观的订阅额度；
  - 录音要提交进仓库才能在 CI 里回放，每刷新一次基线，仓库就多十几 MB；
  - 改提示就要重跑 live 评测：这是有意的代价，但会让提示迭代变慢。
- 什么情况下应该重新考虑：
  - 场景多到一次 live 评测跑不完，或者需要每天跑：换到常驻的集群，或者只抽样；
  - 有了 API key 预算：用 API 后端并行跑，代替订阅；
  - 需要评价自由文本（复盘报告的质量）：再引入裁判模型，但只用在没有结构化答案的地方。
