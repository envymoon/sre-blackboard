# ADR-0010：知识库——Postgres 里的混合检索、本地 CPU 模型、按小节标注的检索评测，知识只能作为背景引用

- 状态：已接受
- 日期：2026-10-28
- 相关里程碑：M6（修复 B12）

## 背景

原型的检索（`app/rag.py`、`app/knowledge.py`）有三个问题：

- **"向量检索"是假的（B12）**。它是把候选倒序以后再跑一遍 BM25，所以"混合"和"消融"都没有意义。
- **语料不对**。4 篇知识文档写的是一个虚构系统（checkout-api、inventory-service、stock-db），和实验环境里的 OpenTelemetry Demo 对不上。
- **没有评测**。检索命中是写死的，重排分数是常数加偏移。

约束如下：

- **只有一个 Postgres**（ADR-0002），而且镜像已经是 `pgvector/pgvector:pg16`。
- **模型调用走订阅额度**，M7 刚因为额度把评测缩小了规模。嵌入和重排如果也走 API，每次入库、每次检索、每次 CI 都要花钱。
- **云端开发容器访问不了 HuggingFace**，但 GitHub Actions 的 runner 可以。
- **按租户隔离**（M1 起每个事件都有 `tenant_id`）。M7 还让每个 Agent 变体用一个租户，所以知识库必须按租户隔离，而且隔离要在 SQL 层面保证。

## 决定

**一、存储：两张表，一个库**

1. 迁移 0005 建两张表：
   - `kb_documents`：每个租户每篇文档一行，记录内容哈希、嵌入模型和切块方式。
   - `kb_chunks`：
     - `tsv` 是生成列：标题和小节名权重 A，正文权重 B；
     - `embedding` 是 `vector(384)`；
     - `sections` 记录这个块包含哪些小节（`RB-PAYMENT#typical-failures`）。
2. **入库是幂等的**。内容哈希、嵌入模型、切块方式三者都没变的文档直接跳过。变了的文档在一个事务里替换全部块，检索永远看不到半篇文档。`--prune` 会删掉目录里已经没有的文档。
3. **不建 ANN 索引**（HNSW、IVFFlat）。每个租户 108 个块，精确扫描只要几毫秒。HNSW 加租户过滤是后过滤，`ef_search` 默认 40 时可能返回不到 k 条。等块数到十万级再加，届时用 pgvector 0.8 的 iterative scan，或者按租户建部分索引。

**二、检索：BM25 + 向量 → RRF → 交叉编码器 → 阈值**

4. 两路召回各取 Top-20，每一路都是一条 SQL，**WHERE 里都有 `tenant_id = :tenant`**。没有不带租户的检索函数，空租户直接报错。向量路还要求块的嵌入模型和查询的嵌入模型一致，换了模型而没有重新入库时，不会拿两个向量空间的距离做比较。
5. **"BM25" 实际是 `ts_rank_cd`**，即覆盖密度排序，没有 IDF，不是真正的 BM25。查询是各个词的 OR：`plainto_tsquery` 会把词 AND 起来，自然语言问题大多一条都匹配不上。评测量出了它的代价（见第七节）。
6. **RRF**：
   - 每个块的分数是它在两个列表里 `1/(60 + 名次)` 之和；
   - 只用名次，不用分数，所以不需要把 `ts_rank_cd` 和余弦距离校准到同一个尺度；
   - k=60 让两路都靠前的块胜过只在一路排第一的块。
7. **重排**：融合后的 Top-20 交给交叉编码器逐对打分，sigmoid 之后按 `SRE_KB_MIN_SCORE` 过滤，再取 Top-k。
   - **"知识库里没有相关内容"是一个合法的回答**，不是错误。
   - 重排失败或超时（5 秒）时退回融合顺序，不做过滤，并标记 `degraded`。重排出问题损失的是精度，不是整个回答。

**三、模型：本地 CPU，ONNX**

8. 嵌入用 `BAAI/bge-small-en-v1.5`（384 维，33M 参数），重排用 `Xenova/ms-marco-MiniLM-L-6-v2`（22M 参数），都通过 fastembed 在 ONNX Runtime 上跑 CPU。
   - 不需要 API key，检索时不联网，**不消耗订阅额度**。
   - worker 镜像在构建时把权重下载进 `/srv/models`，运行时 `SRE_KB_OFFLINE=true`。CI 用 `actions/cache` 缓存权重。
9. `hash` 嵌入和 `overlap` 重排是确定性的替身，接口相同，只给单元测试和下载不了权重的机器用（比如这个云端开发容器）。它们不懂语义，**不能拿来评价检索质量**。

**四、切块：按小节，标注按小节**

10. 文档按 `##`/`###` 标题切。一个小节超过上限，再在段落、列表项、代码块的边界处切，切开的块带上一块末尾 80 个 token 作为重叠；代码块永远不会被切开。嵌入和重排看到的文本前面都加上"文档标题 > 小节名"。
11. **两套参数，由评测来选**：
    - `original`（target 450 / min 200 / max 700 / overlap 80）：原设计的参数，是为长文档设计的。这个语料的文档平均约 300 token，用这套参数每篇只切出 1 块，其中 3 块超过 bge 的 512 wordpiece 上限，向量路会被截断。
    - `section`（min 0）：每个小节单独成块，共 108 块。
    - **默认用 `section`**，理由见第七节。
12. 评测集按小节标注相关性，不按块标注。只要某个结果块包含任一相关小节，就算命中。这样改切块参数不会让标注失效。

**五、给 Agent 用：一个只读工具，和一条引用规则**

13. `kb_search(query, k≤5)` 和其他只读工具走同一个 registry：结果存为证据、有 evidence id、能录制回放。
    - **租户来自工具上下文**（`Source.fetch` 现在会传 tenant），不来自模型给的参数。参数 schema 禁止未知字段，模型没有地方填租户。
    - 返回的每段文本最多 900 字符，按行给出（摘要上限会把单个字符串截到 300 字符）。附带一句说明："这是背景，不是这次事件的数据"。
14. **引用规则**：知识库的结果只能和实时证据一起被引用，不能单独支撑结论。
    - fact、inference、根因候选如果只引用了 `kb_search` 的结果，会被退回重写，仍然不改就丢弃。
    - hypothesis 本来就不需要证据，可以只靠运行手册。
    - 理由：运行手册说的是"通常会怎样"，只有实时数据能说明"这次发生了什么"。复盘里的病因描述得越像，越容易被直接照搬成结论。
15. **默认变体不带知识库**。新增 `rag` 变体：默认变体，加上每个调查员都有 `kb_search` 和一段提示（`prompts/knowledge.md`）。
    - 默认变体的提示和工具一个字都没变，M7 的录音照样能回放。
    - 要不要默认打开，等 live 消融的结果（第七节）。

**六、实验环境**

16. compose 加一个一次性的 `kb-ingest` 服务，用 worker 镜像，在 migrate 之后、worker 之前运行，给 `SRE_KB_TENANTS` 和每个评测租户入库。
    - CPU 上嵌入 108 块要几秒。文档没变时，每次启动都是空操作。
    - M1 的 e2e 任务会构建这个镜像、跑这个服务，所以"镜像里有模型、入库能跑"每个 PR 都会被检查。

**七、检索评测的结果和由此做的选择**

17. 评测集是 `eval/retrieval/queries.yaml`，62 条查询：
    - 20 条精确标识符（错误原文、指标名、开关名）；
    - 16 条换了说法的改写，和答案很少共用词；
    - 18 条调查中会问的问题；
    - 8 条知识库没有答案的负例。

    查询在跑任何检索之前写好，之后没有按结果改过。奇数编号是 dev，阈值只在 dev 上选；偶数编号是 test，只报告。
18. CI 的 `retrieval` 任务用真模型重算整份报告，和提交的 `eval/retrieval/report.json` 比较（数值允许 0.02 的误差，延迟不比较），对不上就失败。"数字是真的、能复现"由 CI 保证，而不是靠 README 里的一句话。
19. 结果（54 条可回答的查询，section 切块）：

    | 模式 | hit@1 | hit@3 | hit@5 | MRR | Top-3 上下文 token | p50 延迟 |
    |---|---|---|---|---|---|---|
    | BM25（ts_rank_cd） | 0.556 | 0.778 | 0.889 | 0.693 | 301 | 2 ms |
    | 向量 | 0.648 | 0.833 | 0.870 | 0.760 | 256 | 8 ms |
    | 混合（RRF） | 0.722 | 0.907 | 0.926 | 0.815 | 294 | 10 ms |
    | 混合 + 重排 | **0.741** | **0.926** | **0.981** | **0.841** | 303 | 667 ms |

    - 每一步都有提升。混合比两路中较好的一路高 7 个点 hit@1，重排再把 hit@5 从 0.926 提到 0.981。
    - 按类别看：
      - BM25 在换说法的改写上 hit@3 只有 0.50；
      - 向量在精确标识符上反而比 BM25 好（hit@1 0.85 对 0.65），原因是没有 IDF 的 `ts_rank_cd` 被错误原文里的常见词稀释了；
      - 混合加重排在精确标识符和调查问题两类上 hit@3 都是 1.00。
20. `original` 切块（每篇一块）的命中率更高（重排后 hit@3 1.00），但这不是同一把尺子：一个整篇块包含所有小节，命中更容易。它每条结果约 320 token，是 section 的 3.2 倍；重排慢 2.2 倍（1.5 秒）；还有 3 块超过嵌入上限。工具对每段的 900 字符限制也会截掉整篇块的大部分。所以**默认用 section**。
21. **阈值是这个重排模型的短板**。MiniLM 交叉编码器（在网页问答上训练）给换了说法的查询打的分接近 0，和无答案的查询分不开：
    - 8 条无答案查询的最高分是 0.015；
    - 有 4 条可回答的查询得分是 0.000。

    在 dev 上按平衡准确率选出的阈值是 0.031（`SRE_KB_MIN_SCORE` 的默认值，有测试把它和报告绑在一起）。在 test 上，8 条无答案查询全部清空，但也清空了 22% 可回答的查询，"首条相关且被保留"从 0.815 降到 0.704。被清空的 10 条全是换了说法的查询（共 16 条），精确标识符和调查问题一条都没有被清空。Agent 多半拿错误原文或具体现象去检索，所以这个取舍可以接受。改进方向写在后果里。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| pgvector + tsvector，都在已有的 Postgres 里 | 不加服务；租户过滤、事务、备份和业务数据一致 | `ts_rank_cd` 没有 IDF；规模大了要处理 ANN 加过滤 | 采用 |
| 专门的向量库（Qdrant、Weaviate）或 Elasticsearch/OpenSearch | 真 BM25、ANN 和过滤做得好 | 多一个有状态服务，多一份租户隔离和备份要做；108 个块用不上 | 不采用：等规模或检索质量真的需要时再说 |
| ParadeDB `pg_search`（Postgres 里的真 BM25） | 有 IDF，还在 Postgres 里 | 换数据库镜像，扩展的运维成本 | 暂不采用：评测显示 BM25 是最弱的一路，是第一个升级点 |
| 嵌入和重排走 API（Voyage、Cohere 等） | 质量更高，不占本地 CPU | 每次入库、检索、CI 都要花钱，要管密钥；离线跑不了 | 不采用：订阅额度是这个项目最紧的约束 |
| 大一点的重排模型（bge-reranker-base，1 GB） | 校准更好，阈值可能更有用 | 镜像和 CPU 延迟都多几倍 | 暂不采用：先用评测证明小模型不够，再换 |
| 知识库内容直接塞进提示（不用工具） | 简单，不用模型决定何时查 | 每个事件都要付全部 token；不相关的内容也进去了 | 不采用 |
| 知识库引用和实时证据同等对待 | 简单 | 复盘写得越像，越会被照搬成结论（"上次是 payment，这次也是"） | 不采用：只能作为背景引用 |

## 后果

- **正面**：
  - B12 修好了：两路召回是真的两路，消融能看出差别，数字由 CI 复现。
  - 不加服务，不花额度，检索时离线可用。
  - 租户隔离在 SQL 里，有测试覆盖。
  - Agent 能用知识库，但用不了"知识库说是这样"来代替证据。
- **负面或代价**：
  - worker 镜像大了约 200 MB，构建时要能访问 HuggingFace。
  - 重排在 CPU 上每次约 0.7 秒。
  - 语料和查询是同一个人写的，有措辞上的偏向，评测数字可能偏乐观。
  - 复盘写的是和评测场景同类的历史事件，`rag` 变体在 live 评测上的提升，回答的是"重复发生的故障"这类问题，不能外推到没见过的故障。
  - 负例只有 8 条，阈值的估计噪声很大。
- **什么情况下应该重新考虑**：
  - 块数到十万级：加 ANN 索引，带 iterative scan 或按租户分区。
  - 精确标识符的查询变多，或 BM25 的 MRR 拖后腿：换真 BM25（`pg_search`）。
  - 阈值清空的可回答查询继续偏多：换更大的重排模型，或者多标注负例重新校准，或者不用阈值，改成低分结果标为"弱相关"。
  - `rag` 变体在 live 评测上没有提升，或者引用违规增多：不默认打开；对"未见过的故障"做留一法（去掉该场景自己的复盘）再测一次。
